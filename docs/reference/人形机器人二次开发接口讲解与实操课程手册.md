**2.开发环境**

**(1). 机器人大脑容器环境开发**

我们将机器人大脑设计为基于 Docker 容器技术的轻量化运行环境。

- 为什么要用容器？ 技术程序、依赖库和运行环境全部打包成一个独立的“微型系统”，实现了环境一致性。

容器化大脑的内部构成（镜像与容器）

- 镜像（Image）：相当于一个只读的系统安装光盘。它是静态的、不可变的模板，定义了大脑里装了哪些操作系统、ROS 中间件和算法库。

- 容器（Container）：相当于正在运行的机器人大脑实例。当镜像被加载启动后，就生成了一个可读写的动态容器。同一个镜像可以同时启动多个容器，用于多机协作或不同场景的测试。

**(2). 主从机分布式开发模式**

我们的机器人采用 ROS通信框架。为了让开发更灵活，可以采用有线网络连接的主从机开发模式。

- 开发范式：机器人本体运行核心进程，而您的开发主机（Ubuntu/ROS1）作为从机，只需通过网线连接机器人，配置好网络环境变量，即可在主机上进行全部代码的编写、编译和调试，无需将代码部署到机器人本体上。
- 关键网络配置（环境变量）：
- ROS_MASTER_URI：固定指向机器人的有线 IP（如 http://192.168.217.1:11311），告诉您的进程“大脑中枢在哪里”。
- ROS_IP：设置为开发主机本机网线连接下的 IP 地址，让机器人知道“谁在找我”。

只要开发主机安装了对应版本的 run 包（中间件数据结构集合包），就能像在机器人本地一样，正常地订阅话题（Topic）和调用服务（Service）。

**(3). 跨平台调用与对外接口（rosbridge）**

除了传统的 ROS 原生开发，我们的“机器人大脑”还向外提供了 rosbridge 协议支持。

- rosbridge是一个基于 WebSocket 的通信桥梁，将 ROS 的通信机制转换为通用的 JSON 格式。
- 适用场景：当您不想安装完整的 ROS 环境，或者使用 Python（非ROS环境）、Java、Web 前端、移动端 App 等跨平台应用时，都可以通过 rosbridge 直接与容器内的机器人大脑通信，实现远程监控、指令下发和数据可视化。

**二 .ROS 1 通信机制**

ROS（Robot Operating System）采用分布式通信框架，节点之间通过三种标准模式进行数据交互，分别适用于不同性质的机器人任务。

1.  话题通信（Topic）

话题采用发布/订阅模式，属于异步、单向的数据传输。发布者将消息持续广播至指定话题，订阅者从该话题接收消息，双方无需等待对方应答。这种机制适用于高频、持续的数据流，典型场景包括激光雷达点云、摄像头图像、惯性测量单元（IMU）数据以及里程计和电池电量等实时状态信息。

\# 实时打印话题数据

\# 查看话题对应的消息类型  
rostopic type /话题名  
\# 手动向话题发布单次消息  
rostopic pub /话题名 消息类型 消息内容  
\# 示例：发布字符串  
rostopic pub /话题名 消息类型 消息内容

rostopic hz /话题名 消息类型 消息内容

1.  服务通信（Service）

服务采用请求/响应模式，属于同步、双向的短事务通信。客户端向服务端发送请求，并阻塞等待直至服务端处理完毕并返回响应。该机制适用于逻辑简单、执行时间短的即时操作，例如查询当前机器人坐标、设置参数、保存地图或开关外设等。

1.  动作通信（Action）

动作采用目标/反馈/结果模式，属于异步、长时且可中断的通信。客户端向动作服务器提交执行目标，服务器立即确认并在后台执行耗时任务。执行过程中，服务器持续发布进度反馈，执行完毕时返回最终结果，同时客户端可随时发送取消指令。该机制适用于导航到目标点、机械臂轨迹规划、自主充电等需要实时进度感知且允许中途停止的复杂行为。

在机器人抓取任务中，获取物体在机器人基座标系（Base Frame）下的精确位姿是实现自主操作的前提。本流程通过视觉感知与坐标变换相结合的方式，完成从图像输入到位姿输出的完整链路。

**步骤一：输入相机数据，输出相机坐标系下的物体位姿**

识别物体并估计位姿：利用目标检测、分割或关键点检测网络识别物体。结合深度信息，通过姿态估计算法得到物体的6D位姿（位置+朝向）；

**步骤二：坐标变换至基座标系**

将物体在相机坐标系下的位姿，依次左乘两组变换矩阵：

- 先乘以CAM2HEAD矩阵（手眼标定矩阵），得到物体在HEAD坐标系下的位姿；
- 再乘以HEAD到BASE的变换矩阵（实时 tf 监听获取），得到物体在机器人基座标系下的位姿。

最终输出即目标物体在基座标系下的位姿。

注：上述计算得到的是物体在基座标系下的位姿，但该位姿对应的是目标物体本身的位置与朝向。直接将该位姿作为机械臂末端执行器（手腕法兰处）的目标位姿通常不能直接用于抓取，原因在于：

- 抓取操作需要末端执行器（如灵巧手）到达物体附近并保持特定朝向才能稳定抓握，而非使tcp与物体中心完全重合；
- 物体自身的参考点（通常为几何中心或质心）与夹爪的抓握中心点之间存在固定的位置与姿态偏差。

因此，在系统设计中应建立抓握中心与tcp点之间的坐标变换关系，即根据物体的形状、尺寸及抓取策略，定义夹爪相对于物体的期望抓取位姿（通常称为“抓取构型”）。该变换关系可表达为：

- 物体在基座标系下的位姿，左乘一个预先定义的抓取偏移变换（抓取点相对tcp），得到末端应到达的目标位姿。

其中，抓取偏移变换需根据实际夹爪尺寸、物体几何特性以及任务要求离线标定或经验设定。

2\. **关节空间运动：**

关节空间：直接以机器人各个关节角度作为控制目标的空间，每个控制点是一组各轴关节弧度值。

**优点**

1.  计算简单，控制器负载低；
2.  不会出现笛卡尔奇异点、腕部翻转问题；

**缺点**

1.  末端运动轨迹不可控：关节同步转动时，法兰 / TCP 走的是曲线，不是直线；
2.  无法精准控制末端走直线、圆弧

**笛卡尔空间运动：**

以机器人基坐标系 X/Y/Z 平移 + R/P/Y 旋转描述末端 TCP 位姿，这套六维描述空间就是笛卡尔空间。

控制器会先做逆运动学，把 TCP 目标位姿换算成各关节角度，再驱动关节同步运动。

- MoveL：两点间强制 TCP 走直线；

**优点**

末端轨迹完全可控，适合焊接、贴合、拾取等需要精准直线 / 圆弧作业场景。

**缺点**

1.  存在奇异点：某些位姿下逆解无解或多解，机械臂抖动、无法运动；
2.  大范围移动时运算量大，速度上限低于关节运动；
3.  容易出现腕部翻转、关节超限。

4\. **安全相关**

**安全保护状态**

**如何触发**

- 当开启碰撞保护，并且各关节超出保护阈值时，会进入安全保护状态。（该阈值可以在配置文件中进行设置）（碰撞保护可以通过接口实时开启或关闭，也可以通过配置文件设置，默认开启）
- 有默认的关节速度和加速度阈值，超过该阈值进入保护状态（该阈值可以在配置文件中配置，该功能无法关闭）

**安全保护状态表现**

当进入安全保护状态时，机械臂（双臂，不包括头腰和升降）呈小范围可拖动状态。（触发检测会判断所有的部位）
